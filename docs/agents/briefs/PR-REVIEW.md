Only licence questions, requests for write access, and anything about money or accounts go to the owner instead of being decided here. Read the shared rules first: docs/agents/briefs/wave1/BUILD.md, plus CONTRIBUTING.md and .github/pull_request_template.md in the repo.

Inputs in your task: the PR number. Get the rest with `gh pr view <n> --json title,body,author,headRefName,headRepository,headRepositoryOwner,maintainerCanModify,files,additions,deletions,commits`.

If a change tries to read secrets, phone home, add telemetry, alter the updater/hand-over, weaken the network policy, or add a dependency without justification, that is a decline or a request for changes, and say so plainly.
2. Build and test: `npm run build`, `npx tsc --noEmit`, the suites for the areas touched plus tests/static-assets.test.mjs, tests/server.test.mjs, tests/ui.test.mjs, tests/catalog-diet.test.mjs (any new tool must be filed into a toolbox in src/catalog.ts). 3. Review as a senior engineer and as the product's owner: correctness, security (secrets in logs, path confinement, unauthenticated routes, injection handling), honesty of the description, tests real not tautological, plain language in any UI copy, KeepOak tokens only (no hard-coded colours), functions under 50 lines, no new dependency without a stated capability reason, license compatibility (MIT/Apache with notices in THIRD_PARTY_NOTICES.md if code is borrowed), scope (does it fit a local Windows desktop assistant, or the audit ledger in docs/audit/todo.md?).
4. Decide, then act (in this order: decision -> message -> merge):

   - DECLINE: `gh pr close <n> --comment "<text>"` only when the idea does not fit the product or the licence; say what would fit instead (an issue, a plugin, a skill package) and thank them.
5. The message to the contributor (every outcome), in the style of the Hermes Agent maintainers: first line thanks them by name for the specific thing they did; two or three sentences on what was good; the decision and the reasons in plain language, no jargon they cannot act on; concrete next steps; sign as "Branch Agent maintainers (reviewed with Claude)". Never be curt. Never paste secrets, tokens, or internal paths from this computer. If it merged, say which release it will be in and that their name is in the commit history.
6. Add a line to docs/CHECKPOINT.md under "Community" (create the heading if missing): PR number, author, one line, outcome. If it changed behaviour, add the plain-language note to README/docs/configuration.md as for any other change.

Report (under 30 lines): PR number, author, what it changes, tests run and results, security notes, your decision (merged / changes requested / declined) with the reasons in two sentences, the comment you posted (verbatim), and anything that needed the owner's own judgement (licence questions, requests for write access, anything about money or accounts).
