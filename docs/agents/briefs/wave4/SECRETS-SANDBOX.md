# Wave 4 task: secrets, sign-ins and isolation that hold up

Rules: docs/agents/briefs/wave1/BUILD.md. Branch: wave4/secrets-sandbox from the local branch wave2/integration. Themes: secrets-and-auth (#69, 30 pieces), sandboxing-and-isolation leftovers (#80). Backend first; small additive settings changes only.

Read: src/locker.ts, src/desktop/settings*.ts (encrypted key storage), src/integrations/shell*.ts, src/integrations/process-usage.ts, src/network-policy.ts, src/policy.ts, src/trust*.ts / content guard, src/receipts*.ts, tests/projects-locker.test.mjs, tests/guardrails.test.mjs.

Build:
1. Secret handling end to end: a single `Secrets` service in front of the locker with typed references (`secret://PROJECT/NAME`) that tools can pass instead of values; the runtime resolves references only at the call boundary (HTTP headers, env for shell, provider keys) and scrubs every value from tool results, events, receipts, logs and errors with one shared scrubber (extend the existing one); rotation (`POST /api/secrets/:name/rotate` stores the new value and records the date); expiry reminders; an audit of which run used which secret (`GET /api/secrets/audit`).
2. OAuth for connections: a generic OAuth 2.0 authorization-code + PKCE flow with a loopback redirect (127.0.0.1 port) usable by channels and app integrations later (Google, Microsoft, GitHub, Slack); tokens stored in the locker with refresh handling; `POST /api/connections/oauth/start` returns the URL, the app opens it in the default browser, the callback completes the flow. No provider-specific UI yet; a test provider (fake authorization server) proves it.
3. Shell isolation on Windows without Docker: run shell commands inside a Windows Job Object with memory/CPU/time limits and kill-on-close (use the existing process-usage sampling as fallback where job objects are unavailable), a restricted environment (only allowlisted variables plus resolved secret references), a working directory pinned to the workspace/project, and an optional "no network" mode implemented by running through a per-command firewall rule is NOT allowed (needs admin); instead document that network isolation for shell is best-effort and provide a `netless` flag that sets proxy env vars to a dead loopback address so common tools fail fast.
4. PII guard (A0875): a detector for emails, phone numbers, card numbers (Luhn), IBANs, national-id patterns in tool results and outgoing channel messages; configurable action (mask, warn, block) per direction; never on by default for the owner's own workspace reads, on by default for outbound channels.
5. Moderation hook (A0877): an optional check of outgoing messages through the provider's moderation endpoint when the provider has one (OpenAI-compatible `/moderations`), off by default.
6. Session locking and re-authentication: the existing lock gets an auto-lock after N idle minutes and a requirement to unlock before revealing or using secrets in a new run when locked.

Tests (tests/secrets-sandbox.test.mjs): reference resolution at the boundary and scrubbing everywhere (grep the whole event log); rotation and audit; OAuth PKCE round trip against a fake authorization server with refresh; job-object limits kill a runaway process and the env is restricted; netless makes an HTTP call fail fast; PII masking on an outbound channel message and not on a workspace read; moderation hook with a fake endpoint; auto-lock timing.

Acceptance: X1 no secret value in any log/event/receipt (test); X2 OAuth proven; X3 job object limits proven; X4 PII guard proven both directions; X5 docs/configuration.md sections in plain language; X6 no new dependency. Report the ids you consider done.
